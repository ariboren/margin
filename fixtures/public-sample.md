# Tile renderer pipeline review

**Date:** 2026-09-12. **Scope:** the vector tile renderer behind the public map viewer, from the `GET /tiles/{z}/{x}/{y}.png` handler down to the style compiler, the glyph loader and the two cache tiers. **Status:** draft for the platform group; numbers are from the staging cluster unless a row says otherwise.

This review started as a question about cost and turned into a question about correctness. The renderer fleet grew from six nodes to twenty-two over the spring without a matching rise in traffic, and the first pass through the dashboards suggested that most of the extra capacity was spent re-rendering tiles that had already been rendered and cached minutes earlier. Following that thread led through the cache key builder, the invalidation fan-out, the render queue and the font loader, and each of those turned out to have its own problem that was independently worth fixing. The findings below are ordered by how much render time they cost us in the sampled week, not by how hard they are to fix; several of the cheapest fixes sit near the bottom of the list because their effect is small even though the change is a single line.

A note on vocabulary before the details. A *tile* is one 256 by 256 image at a given zoom, column and row. A *style* is the compiled JSON document that says how each source layer is drawn, and a *style version* is the content hash of that document after compilation. A *render* is one pass of `renderTile()` that produces a PNG from source data and a style version. The *edge cache* is the CDN in front of the service, and the *origin cache* is the Redis cluster the renderer checks before doing any work. When this document says a tile was *wasted*, it means a render produced bytes identical to a PNG already present in the origin cache under a different key.

## 1. Scope and method

We looked at one week of production traffic (2026-08-25 to 2026-08-31), sampled at one request in fifty, and replayed the sample against a staging cluster with request tracing turned on. Every trace carries the cache key the handler computed, the style version it resolved, whether the origin cache hit, how long the render queue held the job, and the final byte size of the PNG. We joined those traces against the source data change log so that every render could be labelled as either *needed* (source data or style changed since the last render of that tile) or *wasted* (neither changed). The replay harness lives in `tools/replay/` and can be run by anyone with staging credentials; the exact command is in the appendix, and the joined data set is kept in the analytics bucket under `reviews/2026-09-tiles/` for ninety days.

Out of scope: the client-side map viewer, the geocoder, the static basemap exports that the print team generates overnight, and anything to do with billing. We also did not audit the source data ingest itself beyond the point where it publishes a change event; if the ingest publishes a change it did not need to, this review counts the resulting render as needed. That choice undercounts waste, but it keeps the boundary clean, and the ingest team is running its own review this quarter. Finally, we did not load test. Every latency number here is from replayed production traffic at production rates, which means the tail numbers describe the system as it is actually used rather than as it behaves under synthetic stress, and they should not be read as capacity limits.

The method has two known weaknesses. First, sampling at one in fifty hides the long tail of rarely requested tiles, and those are exactly the tiles most likely to miss the edge cache and fall through to the origin. We compensated by running a second, unsampled replay for zoom levels 15 to 18 over a single busy afternoon, and the two replays agree within four percent on every ratio we report. Second, the labelling of renders as wasted depends on the change log being complete, and we found two days in the sampled week where the log had gaps of several minutes during a broker failover. Renders inside those gaps are labelled as unknown and excluded from the percentages, which removes about 0.6% of the sample.

## 2. System overview

The service is a single Go binary, `tiled`, deployed as a stateless fleet behind the CDN. Each request goes through the handler, which normalises the tile coordinates, resolves the style, builds a cache key and checks the origin cache. On a miss the handler enqueues a render job and waits on a per-key channel so that concurrent requests for the same tile share one render. The render worker pool pulls jobs from the queue, loads source features from the vector store, runs the style program over them, rasterises, encodes the PNG and writes it back to the origin cache with a time to live chosen by zoom level. The handler then streams the bytes out with cache headers that tell the CDN how long it may keep them.

### 2.1 Request path

The handler is about 1,400 lines across `handler/`, of which the request path proper is under 300. The rest is error mapping, metrics and the conditional request logic, which is where F9 lives.

The request path is short on paper and long in practice, because each step has grown a special case or two over the years. The coordinate normaliser wraps longitudes and clamps latitudes; the style resolver picks a style by the `style` query parameter, falling back to the account default and then the global default; and the cache key builder concatenates the style version, the coordinates, the pixel ratio and a feature flag bitmap. That last field is where most of the trouble starts, and it is covered in finding F1 below. The handler also honours `If-None-Match` using the cache key as the entity tag, which is correct only as long as the key changes exactly when the bytes change, and the findings show several places where it changes when the bytes do not.

```go
func (h *Handler) cacheKey(req TileRequest, style StyleVersion) string {
	flags := h.flags.Bitmap(req.Account)
	return fmt.Sprintf("t:%s:%d:%d:%d:@%dx:%08x",
		style.Hash, req.Z, req.X, req.Y, req.Ratio, flags)
}
```

The per-key channel that deduplicates concurrent requests is a map of `chan result` guarded by a single mutex. Under normal load this is fine, but when a style is republished every request for every tile misses at once, and the map briefly holds tens of thousands of entries while the queue drains. We measured the mutex hold time during one such event and found it under a millisecond at the median but over forty milliseconds at the 99.9th percentile, which is long enough to show up in the handler latency histogram as a distinct second bump. A sharded map would remove the bump; a simpler fix is to stop republishing styles that did not change, which is finding F2.

### 2.2 Cache tiers

There are two tiers. The edge cache is the CDN, which honours `Cache-Control: public, max-age=N` where `N` comes from a per-zoom table in `config/ttl.yaml`. The origin cache is a Redis cluster with twelve shards, keyed by the cache key described above, holding raw PNG bytes. The origin tier exists because the CDN evicts aggressively for low-traffic tiles, and without it a tile requested once an hour would render every time. In the sampled week the edge hit rate was 91.4% and the origin hit rate on edge misses was 63.2%, which together mean that about 3.2% of all requests reached the render queue. The rest of this review is about why that 3.2% is roughly three times larger than it needs to be.

```bash
# replay one day of sampled traffic against staging and write joined traces
tools/replay/run --from 2026-08-27T00:00Z --to 2026-08-28T00:00Z \
  --target https://tiles.staging.internal --sample 50 \
  --join changelog --out /tmp/replay-0827.parquet
```

Both tiers are sized by hand. The origin cluster was last resized in March, and its memory has sat above 85% since June, which means Redis has been evicting under its `allkeys-lru` policy for most of the period we studied. Evictions are not themselves a bug, but they interact badly with the key churn described in F1: when the same tile is stored under four keys, the cluster holds four copies, and the least recently used of them is evicted first even though it is byte for byte the same as the other three.

### 3.2 Cache key churn (F1 and F3)

Both findings in this section are about the same function, `cacheKey()`, and both come down to a field in the key that changes when the pixels do not.

The cache key was designed in 2023, when the account feature flags were few and all of them affected rendering: `labels.v2`, `terrain.hillshade`, `roads.casing` and a handful of others. Putting the whole bitmap into the key was a reasonable shortcut at the time, because it guaranteed that turning on a rendering flag would never serve a tile drawn without it. Since then the flag registry has become the general mechanism for every product experiment, and the renderer now reads only seven of forty-four flags. Every change to any of the other thirty-seven still rewrites the key, and because flags are flipped per account, one large customer turning on a billing experiment can empty the origin cache for its entire tile footprint in one step. The render fleet then spends the next hour redrawing tiles that are pixel for pixel identical to the ones it just evicted, while the CDN, seeing a new entity tag for each, forwards every conditional request as a full download. We traced the largest single spike in the week, a Tuesday afternoon where queue depth reached 180,000 jobs, to exactly this: a customer with a large fleet-tracking deployment enabled `invoice.split_lines`, which the renderer never reads, and 2.4 million tiles were redrawn over the following ninety minutes. The fix proposed in the table, a render mask built from a tag in the registry, keeps the original guarantee for flags that matter and drops the rest; the build check makes the guarantee enforceable, because a developer who adds a flag read under `internal/render/` without the tag gets a failing build rather than a subtle staleness bug. We considered the alternative of listing render flags by hand in the renderer, and rejected it because a hand list drifts silently, which is how the current state arose in the first place.

Pixel ratio churn is smaller but has the same shape. The viewer requests `@3x` tiles on devices whose screens report a device pixel ratio of three, which is most current phones. The renderer has never supported `@3x` output: `normaliseRatio()` clamps anything above two to two, renders at `@2x`, and the browser scales the image up. The clamping happens after the key is built, so the cache holds both a `@2x` and a `@3x` entry for the same bytes, and the `@3x` entry is written only after a full render. On phones this also means that the first `@3x` request for a tile that is already cached at `@2x` goes all the way to the render queue. Moving the clamp before the key builder fixes both problems, and because the output bytes do not change, no client needs to know.

One subtlety applies to both fixes. Changing the key format on deploy empties the origin cache in effect, since no existing entry matches a new key. We should ship the key change behind a dual-read period: for one day, the handler checks the new key first and then the old one, writing only the new one. The cost is a second Redis round trip on misses for a day; the benefit is that the deploy does not trigger a cold-cache stampede across the whole fleet.

### 3.3 Style republishing (F2)

The style service compiles each style from a directory of YAML layer files into a single JSON program that the renderer interprets. The publisher hashes the source directory, including every comment, whitespace change and file modification time, to produce the style version. Any deploy of the style service, which happens several times a day, touches every source file's modification time through the container build, and so every deploy republishes every style with a new version. The renderer, seeing a new version, correctly treats all cached tiles for that style as stale. In the sampled week there were 212 publishes, of which 171 compiled to a program identical, byte for byte after minification, to the one they replaced.

```ts
// what the publisher should do: hash the program the renderer runs, not the sources
export async function publish(style: StyleSource, store: StyleStore): Promise<PublishResult> {
    const program = minify(await compile(style));
    const version = sha256(program).slice(0, 16);
    if ((await store.current(style.id))?.version === version) {
        return { published: false, version };
    }
    await store.put(style.id, { version, program });
    return { published: true, version };
}
```

The change is contained: the hash moves from the source walker into the compile step, and the publish is skipped when the hash matches what is stored. We ran the week's 212 deploys through a patched publisher offline and got 41 publishes, every one of which corresponds to a real change in a layer file. Nothing outside the style service needs to change, and there is no migration, because the version is an opaque string to every reader. The one risk is that minification is not stable across compiler versions, so an upgrade of the minifier could republish every style once; that is acceptable and much better than the current daily churn, and it can be avoided entirely by hashing a canonical serialisation instead, which `compile.Canonical()` already produces for the diff tool.

### 3.4 Render queue and worker pool (F4, F5)

These two findings do not create waste; they make each miss slower and each new process less useful. They matter most during the spikes that F1 and F2 cause, so their value falls once group 1 lands, but it does not go to zero.

The render queue is a Redis list with `LPUSH` on enqueue and a blocking `BRPOP` in each worker. It has no notion of priority, so the nightly pre-render job, which walks every tile at zoom 0 to 10 for each published style, competes with interactive misses on equal terms. Between 01:00 and 03:00 UTC this puts interactive jobs behind a backlog that peaks near two million entries, and the viewer, which gives up on a tile after five seconds, shows grey squares to users in time zones where that window is the evening. Splitting the queue into two lists and having workers try the interactive list first with a zero timeout, then block on both, gives strict priority in a few lines and keeps the pre-render job's total throughput the same.

Worker start-up is slow for a different reason. Each worker loads glyph ranges lazily, one HTTP request per 256 code points per font, and caches them in a map owned by that worker. A tile with labels in three scripts and two font weights can need a dozen ranges before it can be drawn. Because the map is per worker rather than per process, a process with sixteen workers fetches the same ranges sixteen times, and because the autoscaler adds processes exactly when the queue is deep, the fresh processes spend their first seconds fetching glyphs instead of draining the queue. Sharing the cache per process and prefetching the two Latin ranges for the default font stack removes most of that cost; the readiness probe makes sure the load balancer does not route to a process until the prefetch completes.

The worker pool size is set by `RENDER_WORKERS`, which defaults to the number of CPUs. We looked at whether rendering is CPU bound enough for that default to be right, and it mostly is: rasterisation dominates, and the vector store reads are served from a local cache after warm-up. The exception is label placement for dense urban tiles at zoom 16 and above, where the collision index spends a large share of its time allocating, and a pool size of one and a half times the CPU count gave about 9% more throughput on a replay of a busy afternoon. That gain is real but small, and it is worth revisiting only after F4 and F5, since both change what the workers spend their time on.

### 3.5 Empty tiles, lifetimes and invalidation (F6 to F8)

A large share of the world is empty at high zoom: open ocean, deserts, ice. The source query for such a tile returns no features, and the renderer still allocates a canvas, runs the style program over nothing, encodes a PNG of the background colour and stores it. Every empty tile for a given style version is byte for byte the same image, so the whole class can be served from one precomputed PNG per style version, held in memory. The source store already knows when a query is empty before rendering begins, which makes the short-circuit a check on the length of a slice. Because an empty tile only changes when new data arrives in that area, and the invalidation path already handles that, these tiles can safely take a much longer edge lifetime.

The time to live table has one line in effect. The file lists per-zoom lifetimes in a comment, but the parser reads only `default`, and that has been `3600` since the file was created. Low zoom tiles are few, hot and stable, which is the profile that benefits most from a long edge lifetime; today they expire hourly and a meaningful share of all edge misses are for tiles at zoom five or below. The proposed table gives zoom 0 to 5 a day, 6 to 10 six hours, 11 to 14 two hours and 15 and above the current hour. Style edits are not delayed by longer lifetimes, because the style version is in the key and a new version is a new URL from the viewer's point of view.

Invalidation is the one place where the fix is about speed rather than waste. When the ingest publishes a change, `invalidate.Run()` computes the affected tile set from the change's bounding boxes and deletes the matching keys for every style version. It does so one `DEL` at a time from one goroutine. For a small change this is invisible, but a coastline or boundary update can touch tens of thousands of tiles across all zoom levels, and each delete is a round trip. During the minutes this takes, the origin keeps serving tiles that no longer match the source. Pipelining per shard and switching to `UNLINK`, which frees memory in the background, brings the worst case in the sampled week from nearly seven minutes to under ten seconds in staging.

- `invalidate.Run()` should also emit the size of the affected set as a histogram, so a change that unexpectedly touches millions of tiles is visible before it finishes rather than after.
- The bounding box computation pads each change by one tile at every zoom, which is correct for label bleed across tile edges but doubles the set for point changes; padding only when a label layer is affected would halve the typical set.
- Deletes for style versions that are no longer current are wasted work, since those keys are unreachable once the viewer has the new version; restricting invalidation to the current and previous version per style removes about a third of all deletes.
- The job holds no lock, so two overlapping changes can interleave deletes, which is harmless today but would not be if invalidation ever moved to a rewrite-in-place model.

## 5. Recommendations

The fixes fall into three groups by how they interact. The first group removes key churn and is where most of the saving is: F2, then F1 with its build check, then F3, all behind one dual-read period so the fleet only goes through one key migration. The second group reduces render cost per miss without touching keys: F6, F5 and F4. The third group is hygiene that makes the next review easier: F7, F8, F9 and F10. The groups can proceed in parallel since they touch different packages, but within the first group the order matters for the reason given in section 3.1.

1. Ship F2 first, alone. It has no migration and the largest effect per line. Measure publishes per day and origin hit rate for a week before moving on, so the effect of F1 can be measured separately rather than blended.
2. Add the `render` tag to the flag registry and the build check from the risk register, then land F1 and F3 together behind the dual-read period. Announce the key change in the platform channel a day ahead, because the analytics team parses cache keys from the edge logs and their parser will need the new format.
3. Land F6 with the typed timeout error from the risk register in the same change. Without the typed error the short-circuit is unsafe, and the two should not be separated even briefly.
4. Land F5 and its readiness probe, then F4. The order matters because F5 changes how fast new processes become useful, which changes how much queue depth the autoscaler sees, which is the signal F4's lanes are tuned against.
5. Do the hygiene items in any order. F9 needs a field added to the origin cache value, so it is easiest to land alongside the dual-read change if the timing works out, but it does not depend on it.
6. Rerun the replay from section 1 after each group and record the numbers in the table in section 6, so the next review starts from measurements rather than estimates.

A word on what we are not recommending. We looked at replacing the Redis origin with a disk-backed object store, which would remove the memory pressure described in section 2.2, and decided against proposing it now: once key churn is fixed, the working set should fall to roughly a third of its current size, and the eviction pressure may simply go away. We also looked at moving rasterisation to GPUs, which the vendor pitch suggests would cut per-tile render time by an order of magnitude; our own benchmark on a sample of 10,000 tiles showed a 2.4 times speed-up for dense tiles and a slowdown for sparse ones, because upload and download of small canvases dominates. That is worth a separate study once the waste is gone, since it is the remaining render cost that such a change would be judged against.

The targets above are for the week after group 1 lands, not after all groups. We chose them from the replay: we patched the key builder and the publisher in a staging build, replayed the same sampled week and read the resulting numbers. They should be treated as what the fix can achieve under last month's traffic, not as a forecast, because traffic changes and because the replay cannot model customer behaviour that reacts to faster tiles, such as a viewer that pans more when tiles load quickly. If the real numbers fall short of the targets by more than a few points, the first suspect should be a render-relevant flag that the replay's patched build treated as irrelevant, since the flag tagging was done by reading code rather than by testing each flag.

## 7. Test coverage

Coverage numbers from the build are not useful here: the renderer package reports 81% line coverage, and every finding in this review sits in code that is covered by at least one test. The problem is what the tests assert, not which lines they run.

The renderer's tests are good at the edges and thin in the middle. The rasteriser has golden image tests for every style fixture at three zoom levels, and the handler has request-level tests for coordinate edge cases, but nothing tests the path between them: the cache key, the dedup map, the queue and the write-back. Every finding in this review lives in that middle path, and none of them would have been caught by the existing suite. The table below lists what we propose to add, in the order the fixes land.

| Area          | What exists                                                                                                                             | Gap                                                                                                                                                             | Proposed test                                                                                                                                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Cache key     | `handler/key_test.go` checks that the key contains the coordinates and the style hash, using a fixed flag bitmap of zero for every case | Nothing checks that the key is stable when irrelevant inputs change, which is the property F1 and F3 both violate; the zero bitmap hides every flag interaction | A property test in `handler/key_test.go` that generates random flag sets differing only in untagged flags and random ratios above two, and asserts the key does not change; plus a case per tagged flag asserting that it does |
| Style publish | `style/publish_test.go` covers the store write and the error paths when the store is unavailable, with a mock store                     | No test publishes the same style twice, so the republish-on-every-deploy behaviour of F2 has no failing case                                                    | A test that compiles a fixture style, publishes it, touches every source file's modification time and whitespace, publishes again and asserts `published: false` with the same version string                                  |
| Render queue  | `queue/queue_test.go` checks push and pop ordering against a real Redis started by the test harness                                     | Priority does not exist yet, so there is nothing to test; after F4 the interesting property is that interactive jobs never wait behind pre-render ones          | A test that fills the pre-render lane with a thousand jobs, pushes one interactive job and asserts it is the next one popped, plus a test for the ageing rule chosen in the risk register                                      |
| Glyph loading | None at the unit level; the golden image tests load glyphs from a local fixture directory and never touch the fetch path                | The per-worker cache, the absence of prefetch and the missing checksum validation are all untested                                                              | Tests against an `httptest.Server` that counts range requests, asserting one fetch per range per process, a prefetch at start-up, and a refetch after a range fails its checksum                                               |
| Empty tiles   | Golden images include two ocean tiles, which pass today because they render correctly, just expensively                                 | Nothing distinguishes a successful empty query from a timeout, which the short-circuit in F6 must do to be safe                                                 | A store fake that returns an empty slice in one case and the typed timeout in another; assert the blank is served and cached long only in the first case                                                                       |
| Invalidation  | `invalidate/run_test.go` checks the affected tile set for a handful of bounding boxes at three zoom levels                              | No test covers the delete path's speed or its behaviour across shards, and the padding rule has no case for point changes                                       | A test with a fake cluster that records calls per shard, asserting pipelined `UNLINK` in batches and parallel shards; a table test for padding with and without label layers                                                   |

A final note on the golden image tests: they compare PNGs byte for byte, which has been a steady source of flaky failures whenever the encoder library is upgraded, because a different compression level produces different bytes for the same pixels. Comparing decoded pixels with a small tolerance would remove the flakiness without weakening the check, and it would make the F9 change, which starts hashing PNG bytes for the entity tag, easier to reason about, since the tests would no longer be sensitive to the exact encoder output that F9 depends on.

## 8. Open questions

1. Does the analytics team's edge log parser depend on the exact key format, or only on the coordinates it contains? If only the coordinates, the key change can ship without coordinating a parser release, which would remove the one cross-team dependency in group 1.
2. Should the blank tile for a style version be served with its own entity tag, shared across every empty tile, or with a per-coordinate tag? A shared tag lets clients reuse one cached blank everywhere, which is good, but some older viewer builds key their local cache by entity tag alone and would show the wrong tile if a non-empty tile ever shared it by mistake.
3. Who owns `config/ttl.yaml` after the change? Today nobody does, which is how the per-zoom lines stayed in a comment for two years. The platform group is the obvious owner, but the lifetimes interact with CDN pricing, which the infrastructure group negotiates.
4. Is a day the right lifetime for zoom 0 to 5, or should it be longer? The data supports a week for most of those tiles, but boundary disputes make a few of them sensitive, and a week-long stale tile of a disputed region is a worse outcome than the cost of more frequent refreshes.
   - If a week, the automatic purge from the risk register becomes mandatory before F7 ships, not a nice-to-have.
   - If a day, the manual purge remains an acceptable fallback, and the automatic purge can follow later.
5. Should `tiled` stop accepting `@3x` requests entirely and redirect them to `@2x`? That would make the ratio clamp visible to clients and save the key normalisation, but a redirect costs a round trip on every tile for high density phones, which is exactly the population we most want to serve quickly.

> The shortest summary of this review is that the cache key says more than the tile does. Every field in it should be there because changing that field changes the pixels, and today three of its fields change far more often than the pixels do.

One last observation about process rather than code. Every finding in this review was visible in some dashboard for months before anyone connected it to fleet size, and the reason is that each dashboard answered its own narrow question well: the cache panel showed hit rates, the queue panel showed depth, the flag service showed flag changes, and the style service showed deploys, but nothing put those four timelines next to each other, and nothing labelled a render as wasted or needed. The replay join is what made the pattern obvious, because it turned a vague sense that the fleet was too large into a single number with a breakdown by cause, and each cause pointed at a specific function. We recommend keeping the weekly replay running after the fixes land, not as an audit but as a standing metric, since the conditions that produced this waste are ordinary: a shortcut that was right when it was written, a registry that grew a second purpose, a build step that changed a timestamp nobody thought mattered. Each of those will happen again in some form, and a wasted render share that creeps up from fifteen percent to twenty-five is much easier to trace in the week it happens than a year later, when several causes have piled up and the fleet has quietly grown to absorb them. The cost of the weekly run is a few hours of staging time and one parquet file, which is small next to a single extra render node.
